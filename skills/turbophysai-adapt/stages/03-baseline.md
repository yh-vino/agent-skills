# 03 Baseline 与 Profiling

目的：得到后续所有收益的计算基准，并用 profiling 找出时间花在哪里。

产出：《优化报告》第 4 章（4.1 Baseline 配置、4.2 正确性与精度验证、4.3 性能对比、4.4.1 HCU Profiling、4.4.2 竞品 Profiling）；工作区 `traces/`、`logs/`。

## 步骤

1. **对齐配置（4.1）**：逐项填写竞品与 HCU 的卡数、并行策略、micro / global batch、dtype、输入尺寸和训练超参；不一致的写原因。
2. **精度验证（4.2）**：按 2.4.2 跑 HCU Baseline 和竞品，附 loss / grad norm 对比曲线。Baseline 出现精度问题时先定位解决，不进入优化；项目急时可以精度定位与性能优化分人并行，但优化结论要等精度问题解决后再确认。
3. **性能对比（4.3）**：按 2.4.3 的口径测速，**不开 profiler**。单卡和多卡都测，用扩展效率（多卡吞吐 / 单卡吞吐 × 卡数）区分计算问题和通信扩展问题。
4. **采集 trace**：给用户下面的采集要求，HCU 和竞品各采一份：
   - CPU + 设备活动，所有 rank 都导出，文件名 `trace_rank_<rank>_*.json`，同一次运行、同一窗口；
   - `schedule(skip_first=<越过编译与预热>, wait=1, warmup>=5, active=3)`；
   - **计时用的 trace 不开 `with_stack`**；需要把同步点、拷贝定位到代码行时，另采一份带栈的，不用它的时间做比较；
   - 采集时关掉数值检查和模型保存，保证设备空闲；
   - 用到 `torch.compile` 的，另跑一次短训练采 `TORCH_LOGS=graph_breaks,recompiles` 日志（不和 trace 同一次运行）。

   采集后检查：rank 文件数等于卡数；每个文件有 3 个左右 `ProfilerStep`；有 kernel 事件；各 rank 文件大小接近。
5. **统计（4.4.1）**：按模板分类拆解每步耗时，分母统一为 step 时间：计算（GEMM）、计算（Attention）、计算（triton）、计算（其他 kernel）、通信（未被掩盖部分）、数据加载、Host 侧开销 / 设备空闲；再给 Top-10 kernel（调用次数、总耗时、占比）。
   - 空闲时间要继续归因：launch 小间隙、等同步（`.item()`、`nonzero` 等调用期间 GPU 空闲）、等 H2D 拷贝、等数据、等通信。这部分是阶段 04 最常见的瓶颈来源。
   - 只采了一次、每个 rank 取一个 step 时，结论是“单次样本”，报告里注明。
   - 标注每个数字的来源：`[实测]` 来自 trace 事件，`[推断]` 来自归因规则，`[上限]` 是可回收时间的上限估计。
   - trace 统计脚本还在编写中；在它就绪之前，用 `torch.profiler` 的 `key_averages()` 表和 trace 时间线手工拆解，并在报告里写明方法。
6. **竞品对比（4.4.2）**：用同样的维度拆解竞品 trace，列出差异项（某类 kernel 耗时差几倍、通信占比差多少），直接作为阶段 04 的瓶颈输入。

## 常见问题

- trace 里的 step 时间比测速结果长：profiler 本身有开销，带栈时更明显。性能数字只用第 3 步的测速结果。
- 分类拆解各项加起来不等于 100%：说明有 kernel 没分类或有重叠，未分类占比超过 5% 时补分类规则再统计。
