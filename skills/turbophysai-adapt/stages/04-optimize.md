# 04 瓶颈与优化（循环）

目的：按瓶颈排行逐项优化，每一项都有证据、有独立开关、有精度结论、能算出增量收益。

产出：《优化报告》第 5 章（5.1 瓶颈分析、5.2 收益汇总、5.3～5.8 各 OPT、5.9 未采纳的尝试）；`state.json` 的 `bottlenecks[]`、`optimizations[]`；代码改动。

## 进入循环前

1. **列瓶颈（5.1）**：从 4.4.1 的分类拆解、空闲归因和 4.4.2 的差异项生成 BOT 条目，每条写描述、类别、证据（引用 4.4 的表或 trace 文件）、耗时占比、预估收益上限。按耗时占比排序。暂不处理的也要列，并写原因。
   - 预估收益只是上限：不同 BOT 可能覆盖同一段空闲，不能相加。
2. **第一个 OPT 先看公共件**：阶段 02 里已生效但属于性能优化的公共 Group，作为 OPT-01（类别按其内容），单独测出收益。

## 每一轮（一次推进一两个 BOT）

1. **定位到代码**：
   - 同步点、H2D 拷贝、小 kernel 密集区：用带栈 trace 找到 `file:line`；没有栈时只写到外层算子链，并注明“未定位到代码行”，不猜。
   - 计算热点：Top kernel 反查到模块（kernel 名、调用它的 aten 算子、所在 module）。
2. **先找已有实现**（按顺序，找到就停）：
   1. `turbo_physai/optimizations/common/` 里有没有同目标或同功能的 Group → 直接启用；
   2. 其他模型的 Catalog 是否替换过同一个框架入口（`grep -rn "<target>" turbo_physai/optimizations/models/*/catalog.py`）→ 不要另写一份，按 landing.md 第 2 节合并成公共实现；
   3. `turbo_physai/operators/` 有没有可用算子。
3. **选手法**：按 BOT 类别查 [patterns/index.md](../patterns/index.md)，读对应的仓库案例代码，判断前提是否成立（shape、dtype、是否在 compile 区域内、多卡一致性、数值是否变化）。
4. **给方案，等用户确认**：写出 OPT 草案——对应 BOT、问题描述（含证据）、优化原理、落地位置（common / models / 补丁）、Group 划分、开关、是否改变数值、验证方法。用户同意后再改代码。
5. **按 [landing.md](../landing.md) 落地**：写 Replacement 和 Catalog 声明，更新 recipe，重新生成配置。
6. **验证这一项**：
   - 接入：`turbo-physai run --log-report ...`，确认新 Group 为 `applied`，其他 Group 状态没变。
   - 正确性：计算改写要做输出和梯度对比（公共件必须有单测，模型专用件至少本地验证）；带 `runtime_condition` 的两个分支都要测。
   - 快速精度：短时 loss 和 Baseline 对比（2.4.2 训练过程层级）。数值会变的（TF32、非确定性算法）标 `accuracy_only` 并在 OPT 里写清精度影响。
   - 收益：按 2.4.3 测速，不开 profiler。单项收益用 `--disable-group <本 OPT 的 Group>` 做对照；累计收益按 OPT 叠加顺序记录到 5.2。
7. **记录**：填 OPT 小节（对应瓶颈、问题描述、优化原理、实现方案（Group ID 和开关）、收益数据、精度验证、适用范围与限制、是否可复用）；更新 `state.json`。只在某些 batch、分辨率、卡数下有收益的，写明适用范围。
8. **失败或负收益**：保留编号，状态 `rejected`，写进 5.9（预期收益、实际结果、未采纳原因），代码改动撤回。
9. **每做完一到三个 OPT 重新采一次 trace**，用同样的方法统计，更新 BOT 排行。旧瓶颈消失后，新的排行可能完全不同。

## 退出条件（门禁）

- [ ] 达到 1.3 的性能目标；或剩余 BOT 都已标 `deferred` 并写明原因（收益上限太小、需要厂商支持、超出范围）。
- [ ] 每个 `validated` 的 OPT 都有精度结论和独立开关。
- [ ] 环境变化（驱动、SDK、框架升级）带来的收益单独记在 5.8“其他优化”，没有混进 OPT。

## 常见问题

- 一次改了好几处再测：收益和精度问题都无法归因。拆成多个 OPT，逐个验证。
- 编译开启后首次运行很慢：首次编译开销与稳态分开统计，测速前充分预热。
- 优化依赖私有接口或特定版本：用 `compatibility_check` / `runtime_condition` 检查前提，不满足时回退原实现（评审清单 B 第 11 项）。
